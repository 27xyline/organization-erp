Срез 2026-10-07, HEAD `4dfa96d`; только этап 00. Текущий владелец всех бизнес-записей — существующий TypeScript/Prisma backend, CLI и TS notification worker. Python writer отсутствует. Будущие этапы ниже не предоставляют текущих гарантий.

Реестр содержит **105 writer операций/entrypoints**: **97 с прямыми DB actions**, 8 делегирующих цепочек; **281 direct model mutation site**, **2 raw SQL write site** (оба outbox) и **20 nested relation mutation syntax site**. Дополнительно 7 файловых/SMTP/telemetry/log effect entries. Это количество статических sites, не runtime операций/строк БД. Nested actions/cascade SQL effects не суммируются в281. E2E setup учитывается отдельно от production сценариев.

Полные точные model/action/line/tx/lock/audit/scope/caller поля: [write-owners.json](write-owners.json). Не выполнены DB/concurrency tests, fixture mutations, email или storage writes; доступные проверки и копии описывает [baseline-validation](../../baseline-validation.md). Scope guards route-level — в [frontend-callers.json](frontend-callers.json) и api-contracts.

## Ограничения outbox DB baseline: fixture isolation и время

Read-only разбор текущих tests/service/schema подтверждает: [enqueue fixture](/Users/mac/Desktop/organization-erp/src/features/notifications/application/outbox.integration.test.ts:24) не задаёт availableAt (используется [TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP](/Users/mac/Desktop/organization-erp/prisma/migrations/20260718170000_add_notification_platform/migration.sql:57)), но истёкший lease задаёт через Node `Date.now()-1000` на строке43. [claimNext](/Users/mac/Desktop/organization-erp/src/features/notifications/application/outbox.service.ts:36) проверяет attempts<5, availableAt<=PostgreSQL NOW и expired/null lease для PROCESSING. Перед claim выполняется отдельный terminal cleanup UPDATE:69. Без измерения обоих eligibility predicates пропущенную fixture нельзя приписать конкретному clock/default поведению.

Suite имеет только [beforeAll/afterAll](/Users/mac/Desktop/organization-erp/src/features/notifications/application/outbox.integration.test.ts:12), одного userId и одинаковые SYSTEM/Test payload; per-test cleanup отсутствует. claimNext выбирает глобальную очередь, ORDER BY availableAt,id, limit1. Поэтому запись, оставшаяся после прерванного второго теста, может попасть в третий, несмотря на последовательное исполнение файлов. Newly enqueued attempts5 запись сама claimable не бывает. Одинаковый sender payload в логе не идентифицирует строку. afterAll удаляет test user и [FK cascade](/Users/mac/Desktop/organization-erp/prisma/migrations/20260718170000_add_notification_platform/migration.sql:93) очищает очередь уже после suite; поздний SELECT не реконструирует состояние перед failed claim. Это доказанные границы тестовой изоляции, **не доказательство причины конкретных baseline failures**.

Округление TIMESTAMP(3), Node/PostgreSQL clock skew и ACK count0 остаются различными диагностическими гипотезами, пока не получены timestamps/predicate results/identity выбранного item. Failure `sent=0` сам по себе допускает как отсутствие candidate, так и ACK updateMany count0. В stage00 product/test код не исправлялся; текущие результаты выполнения принадлежат baseline-validation, а не этой статической гарантии.
