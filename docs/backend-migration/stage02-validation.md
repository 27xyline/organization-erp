# Этап 02: SQLAlchemy mapping и Unit of Work

Проверка выполнена 8 октября 2026 года на ветке `fastapi-runtime-foundation`. Реализация этапа проверена; учебный разбор этапа ожидает пользователя. Следующий этап не начат.

## Что реализовано

SQLAlchemy mapping описывает все **51 таблицу**, **512 колонок**, **29 PostgreSQL enum**, **132 индекса**, **90 внешних ключей** и **53 CHECK constraints** из inventory. Имена таблиц и camelCase колонок сохранены. Реестр импортирует модели до использования связей. `@updatedAt` перенесён в клиентские `default`/`onupdate`; даты остаются `DATE`, timestamp-колонки — без timezone и с миллисекундной точностью, Decimal сохраняет precision/scale.

Строковые ID генерируются в формате из 25 lowercase букв и цифр, совместимом с ожидаемой CUID-формой в существующих Zod-схемах. Генератор не обещает побайтное совпадение с Prisma CUID или совпадающий порядок ID.

Nullable JSONB требует различать два значения: Python `None` означает SQL `NULL` благодаря `none_as_null=True`; `JSON.NULL` записывает JSON `null`; `{"nested": None}` сохраняет `null` внутри JSON-объекта. Это проверяется отдельным тестом на PostgreSQL и тестом аудита через UoW.

Domain ports — обычные `Protocol` и frozen dataclass с JSON-типами из стандартной библиотеки. Они не импортируют FastAPI, SQLAlchemy или Pydantic. SQLAlchemy UoW скрывает `AsyncSession`, даёт typed audit/notification ports и создаёт отдельную сессию для каждого вызова factory. Успешная операция вызывает один явный `commit`; выход без `commit`, исключение или отмена откатывают транзакцию и закрывают сессию. После terminal commit/rollback UoW нельзя использовать повторно.

Вложенная операция получает тот же UoW и не начинает отдельную транзакцию. Два одновременных UoW используют разные сессии и соединения. AuditLog и Notification/Outbox добавляются в транзакцию вызывающего UoW; адаптеры не коммитят сами. Реальная бизнес-обработка уведомлений, delivery worker, API, авторизация и RBAC остаются за пределами этапа 02.

## Проверки и границы результата

Локальная `erp_stage02_test` содержит schema-only копию схемы из 41-migration source copy. Integration-тесты выполняются на PostgreSQL внутри внешней транзакции и откатываются; после прогона не осталось строк focused JSON-null теста. Полный Python набор: **40 passed**, включая интеграционные проверки на PostgreSQL. Ruff check, Ruff format check и mypy прошли. CI backend job подготавливает отдельную тестовую схему через Prisma migration chain.

Read-only Alembic metadata comparison завершился сообщением `No schema differences detected`. SQLAlchemy/Alembic предупреждает, что не может сортировать циклические FK между `departments`, `employees` и `staff_schedule`; отдельный каталог-тест сравнивает все 90 FK напрямую, включая этот цикл. Сверка metadata не проверяет тела SQL-функций и четырёх inventoried-триггеров, поэтому их эквивалентность и runtime-поведение остаются отдельной задачей.

Локальный снимок баз после проверок: `project1` — 50 public tables и 38 завершённых Prisma migrations; `erp_migration_20261007` — 52 tables и 41 migration; `erp_stage02_test` — 52 tables, включая `_prisma_migrations`, без записей migration history, так как он создан schema-only restore. Ни в одной из них не было `alembic_version`. Исходная БД не использовалась для проверок и не изменялась. Prisma остаётся владельцем DDL до этапа 14.

В ходе подготовки был запущен встроенный `alembic check`: без revisions он создал пустую `alembic_version` в изолированной тестовой БД. Эту пустую таблицу удалили. Повторная проверка использует отдельный read-only comparator, который устанавливает `SET TRANSACTION READ ONLY` и не выполняет DDL. Guard в `env.py` работает только для команд, загружающих Alembic environment; обычная команда `alembic revision` без `--autogenerate` обходит guard. Workflow запрещает создавать revisions до этапа 14, поэтому её не запускали.

## Как разбирать слой и границы

ORM описывает форму данных и связи между строками. Он сам по себе не является доменной моделью: права, бизнес-переходы статусов и orchestration остаются в application/domain-слое. Domain port описывает нужную операции возможность (`append audit`, `enqueue intent`), не раскрывая типы БД.

UoW — граница одной прикладной транзакции. Внутри неё несколько repository/port операций могут записать бизнес-строку, аудит и outbox; они вместе фиксируются только явным `commit`. Если commit забыли или операция падает после первой записи, выход из контекста откатывает всю пачку. Вложенный вызов принимает тот же UoW, иначе он мог бы зафиксировать только часть операции. Параллельные запросы получают разные сессии: одна `AsyncSession` не является безопасной общей рабочей областью для конкурентных задач.

В этой стадии реализованы минимальные persistence adapters для audit и notification intent, чтобы проверить общую транзакцию. Здесь ещё нет переноса бизнес-сервисов и доставки уведомлений; их поведение нельзя считать перенесённым только потому, что ORM-строки успешно записываются.
